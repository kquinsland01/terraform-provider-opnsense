## Intent

**Problem:** Stable core exposes the Kea DDNS general settings singleton, but it lacks an independent Terraform owner and read-only lookup. Completed DHCP subnet/option work does not own these settings or prove safe settings lifecycle.

**Approach:** Implement `opnsense_kea_ddns_settings` for exactly four `ddns.general` fields, fixed import identity `ddns`, targeted partial writes, durable confirmed/uncertain-save recovery and state-only destruction. Prove actual Core state/private persistence and disabled-appliance lifecycle with independent observations and exact restoration.

## Boundaries & Constraints

**Always:** Use official `/api/kea/ddns/get`, `/api/kea/ddns/set` and `/api/kea/service/reconfigure`; verify stable OPNsense >=26.7.7 identity and readable compatible fields before mutation. Own only `ddns.general.enabled`, `manual_config`, `server_ip`, `server_port`. Require explicit enabled intent; preserve omitted optional imported/prior values, explicit false, and unresolved unknowns. Serialize mutations/recovery with the existing client mutex, preserve configured GET retries, reject redirects and issue POST writes once. Retain known singleton identity/state and requested-field-bound recovery intent after saved/uncertain writes. Destroy is strictly state-only, including with pending recovery. Public artifacts are consumer-neutral; exact appliance identity, runtime credentials and raw evidence remain private. Keep implementation, live proof, merge, release and operator adoption distinct.

**Never:** Enable production or lab DHCP/DDNS traffic for this work; infer actual DNS updates from stored settings; manage DHCPv4/6 settings, generic options, parent links, Control Agent, hooks, manual configuration files or private integrations. Never treat zero/empty port as clearing, unknown as false/default, omitted optional arguments as a reset, HTTP success as sufficient save/activation proof, malformed singleton truth as absence, or destroy as a stop/reset/reconfigure. No XML provider writes, automatic non-idempotent retry, unverified activation, shared transport mutation or older-core/OpenTofu claim. Do not invent exclusive locking against out-of-band edits or allow broad filtered-GET ownership.

## Design Notes

This singleton already exists: Create expresses explicit desired settings over a strictly observed baseline, not allocation of another daemon or an implicit reset. Required enabled makes the service-state choice explicit. Optional/computed values are not reset by omission, including at creation; preserve actual appliance values rather than imposing fresh defaults. Empty ports/addresses are invalid required model values, not a supported clear operation. `any` is a real upstream NetworkField sentinel, not an invented address alias.

A saved-but-unactivated singleton is still owned after an error. State-only destruction intentionally abandons that ownership without stopping, resetting or activating anything; backup/review/reimport remains the operator's reconciliation boundary. Never claim recovery can prevent Core's normal failed-create taint/replacement plan.
