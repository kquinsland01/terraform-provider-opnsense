# opnsense_system_gateway_group (Resource)

Manages a Routing gateway group by UUID on **stable OPNsense 26.7.7 or newer**.
The provider verifies firmware identity and a usable gateway-group model before
mutating configuration. API credentials need read access to
`/api/core/firmware/status`, the Routing group model/get/search endpoints and
permission for Routing group add/set/del/reconfigure actions. Use the appliance's
API permission selector; no separate ACL identifier is assumed.

Tier members are individual **gateway names**, not UUIDs or display labels.
Individual gateways must already be configured and reconfigured before their
names become available in group selectors. The upstream gateway selector uses
an independent 20-second cache: route reconfigure alone does not invalidate it.
Before adding or updating a group, this owner waits up to 30 seconds for the
planned names to appear in authoritative model option keys. Polling is read-only
and respects cancellation; unavailable names are diagnosed without a save.
This resource does not own individual gateways. `name` is immutable; changing it replaces the group. At least one member
across the five tiers is required. Omitted optional tiers default to empty sets;
explicit empty sets clear tiers 2–5 without changing the other tiers.
**Upstream limitation:** the stable API ignores empty updates to a populated
`tier_1`. This owner rejects that transition before saving any fields, retaining
the UUID and authoritative values. Do not omit or empty an already-populated
`tier_1` expecting it to clear. A group created with empty `tier_1` and a nonempty
later tier is valid, and its already-empty first tier can remain empty on update.
An explicit replacement is a separate dependency-sensitive operation, never an
automatic clear workaround. Omitting
`pool_options` or `description` owns their empty/default values. Unknown members
cannot be interpreted as clears. No cross-tier uniqueness or address-family
restriction is imposed by the provider.

Saving activates **interface routes only**. It does not apply PF rules. Actual
traffic failover/load balancing, OpenTofu, and older-core behavior are unverified.
Offline protocol tests and API availability do not establish live support;
see the support matrix for the current acceptance gate.

## Example Usage

```terraform
# Gateway names refer to existing individual gateways, not their UUIDs.
resource "opnsense_system_gateway_group" "example" {
  name         = "example_failover"
  tier_1       = ["EXAMPLE_PRIMARY"]
  tier_2       = ["EXAMPLE_SECONDARY"]
  trigger      = "downlosslatency"
  pool_options = ""
  description  = "Synthetic failover group"
}
```

## Schema

## Recovery and dependencies

Confirmed saves retain the UUID and committed values even if read-back or route
activation fails. Private Terraform state records pending recovery across
provider restarts. Preserve the returned state and run a fresh refresh/plan/apply;
recovery activates the saved operation without repeating its add/set/delete.
An uncertain update retains its exact attempted payload privately. Only a matching
authoritative object is activated during recovery. A valid mismatch retains the
actual values and clears uncertainty without activation or another save, allowing
a fresh normal plan; missing/malformed truth retains uncertainty and identity.
If the object stays absent, repeated refresh cannot prove the attempted save:
independently verify the outcome and manually reconcile through supported
Terraform operations rather than blindly recreating it.
An uncertain add is adopted only when an authoritative before/after search finds
exactly one new complete payload match. Unresolved/contradictory outcomes fail
closed: inspect the appliance and import the exact UUID rather than blindly
recreating it. Do not edit recovery bytes or discard tracked identity.

Malformed/unavailable API responses retain existing state. A group referenced by
persisted configuration cannot be deleted; remove its references first, then
retry destroy. Confirmed deletion with failed activation retains identity and a
pending delete marker until authoritative absence and activation are verified.
If that UUID reappears after a restored configuration, recovery retains its actual
values and clears delete uncertainty without activation; a fresh normal destroy
can then delete it. An uncertain delete with a still-present object likewise
reconciles successfully on refresh instead of blocking subsequent destroy.
A lookup never activates changes.
